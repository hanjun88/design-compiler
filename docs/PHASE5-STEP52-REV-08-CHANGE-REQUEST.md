## 1. 变更项 1：RENDER-11A 拆分

### 1.1 问题陈述

REV-07 §10 RENDER-11A 定义为"$w_c \le 0$ 裁切断言"，但该定义将两类物理机制不同的裁剪条件合并为一项：

| 机制 | 数学条件 | 物理含义 |
|---|---|---|
| 齐次坐标退化 | $w_c \le 0$ | 顶点在相机后方或相机平面上，透视除法无效或除零 |
| 近平面边界 | $z_c < -w_c$（且 $w_c > 0$） | 顶点在相机与近平面之间，透视除法有效但超出近平面 |

合并定义导致：
- 测试实现者不清楚应验证哪类机制
- 部分可见组（验证 $z_c < -w_c$）被误认为验证了 $w_c \le 0$
- $w_c = 0$ 精确边界情况被忽略

### 1.2  proposed 拆分定义

#### RENDER-11A-1：齐次坐标退化裁剪（$w_c \le 0$）

| 属性 | 定义 |
|---|---|
| 验证目标 | 当图元所有顶点满足 $w_c \le 0$ 时，硬件完全剔除该图元，可见片段数 = 0 |
| 测试组 1（$w_c < 0$） | 完全不可见对照组：3 顶点相机空间 $z=+0.5$ → $w_c=-0.5 < 0$ |
| 测试组 2（$w_c = 0$ 边界） | 新增：3 顶点相机空间 $z=0$ → $w_c=0$（恰好在相机平面上） |
| 断言方式 | 1. 每个顶点完整 clip-space 四元组（手工计算或 uniform 回读）<br>2. $w_c$ 符号分类显式断言<br>3. 可见片段数 = 0（readPixels 原始输出）<br>4. 原始顶点完整提交 GPU，无 CPU 预剔除 |
| 失败断言 | 若可见片段数 > 0，测试失败并输出非背景像素位置和数量 |

#### RENDER-11A-2：近平面边界裁剪（$z_c < -w_c$，$w_c > 0$）

| 属性 | 定义 |
|---|---|
| 验证目标 | 当顶点满足 $w_c > 0$ 但 $z_c < -w_c$ 时，硬件平截头体裁剪保留可见部分 |
| 测试组 | 部分可见组：A $(-0.5,-0.5,-0.5)$ → $w_c=0.5, z_c=-1.611$（$z_c < -w_c$）；B/C 可见 |
| 断言方式 | 1. A 顶点完整 clip-space 四元组，显式断言 $w_c > 0$ 且 $z_c < -w_c$<br>2. 硬件裁剪保留可见部分（可见片段数 > 0）<br>3. 与完全不可见组结果不同<br>4. 无 CPU 预剔除/预裁剪（原始顶点数据完整保留）<br>5. 原始 readPixels 输出 |
| 失败断言 | 若可见片段数 = 0（整个三角形被丢弃），或存在 CPU 预剔除证据，测试失败 |

#### RENDER-11A-3（可选）：双机制同时存在的分类与诊断

| 属性 | 定义 |
|---|---|
| 验证目标 | 当图元同时包含 $w_c \le 0$ 顶点和 $z_c < -w_c$（$w_c > 0$）顶点时，硬件裁剪行为正确 |
| 状态 | 可选，不在本阶段强制要求 |

### 1.3 拆分后的验收矩阵

| 编号 | 验证目标 | 当前单元测试 | 当前 E2E | REV-08 后要求 |
|---|---|---|---|---|
| RENDER-11A-1 | $w_c \le 0$ 裁剪 | ❌ 无 | ⚠️ 间接（$w_c<0$，缺 $w_c=0$） | 必须：独立测试 + $w_c=0$ 边界 + 显式断言 |
| RENDER-11A-2 | 近平面 $z_c$ 边界 | ❌ 无 | ✅ 已覆盖 | 必须：显式 $w_c>0$ 且 $z_c<-w_c$ 断言 |
| RENDER-11A-3 | 双机制分类 | ❌ 无 | ❌ 无 | 可选 |

### 1.4 必须补交的证据

每个测试必须提供：
1. 每个测试顶点完整的 clip-space 四元组 $(x_c, y_c, z_c, w_c)$
2. $w_c$ 符号分类（$w_c < 0$ / $w_c = 0$ / $w_c > 0$）
3. $w_c = 0$ 边界样本（RENDER-11A-1 测试组 2）
4. 明确的失败断言（可见片段数阈值 + 非背景像素位置）
5. 原始 readPixels 输出（保存为证据文件）
6. 测试 ID 与契约条款的对应关系

## 2. 变更项 2：公共 API 归属

### 2.1 问题陈述

`setRenderMode(mode: RenderMode)` 和 `setRenderMesh(mesh: TriangleMesh)` 是 `GlPipeline` 类的 `public` 方法，`GlPipeline` 被 `export class` 导出。但 REV-07 契约未定义这两个方法。

### 2.2 调用范围审计结果

全仓库搜索 `setRenderMode` / `setRenderMesh`：

| 位置 | 类型 | 说明 |
|---|---|---|
| `chinese-aesthetic/render/gl-pipeline.ts:145,156` | 定义 | public 方法定义 |
| `tests/chinese-aesthetic/render/e2e/real-webgl-execution.spec.js:268-269,402-403,421-422,456-457` | 调用 | E2E 测试，4 组调用（NDC 验证、部分可见、完全不可见、黄金帧） |
| `tests/chinese-aesthetic/render/e2e/render-pipeline.bundle.js:1151,1161` | 编译产物 | bundle 中的定义（非调用） |
| `docs/REMEDIATION-CLARIFICATION-03.md` | 文档引用 | 非调用 |

**结论**：
- 唯一的调用者是 E2E 测试本身
- 没有任何生产代码或外部模块调用这两个方法
- 没有仓库外部消费者

### 2.3 Proposed 处置方案

**方案 A（推荐）：标记为 @internal，明确内部实现地位**

理由：
1. 这两个方法仅用于 E2E 测试中配置渲染模式和网格，不是面向最终用户的 API
2. 没有外部消费者
3. 它们是渲染管线内部状态配置的一部分，不应构成 ABI 扩展

执行动作：
1. 在 `gl-pipeline.ts` 中为 `setRenderMode` 和 `setRenderMesh` 添加 `@internal` JSDoc 标注
2. 在文档中明确说明这两个方法是内部实现细节，仅供测试和内部管线使用
3. 补充 API surface 测试，验证公开 API 边界不包含这两个方法（或明确标注为 internal）
4. 不修改方法的 `public` TypeScript 修饰符（E2E 测试需要通过 `window.RenderPipeline` 全局对象访问），但通过文档和 API surface 测试明确其内部地位

**方案 B：纳入 REV-08 正式公开 API**

如果审查席认为这两个方法应作为公开 API，则需在 REV-08 中定义：
- 方法签名和参数约束
- `RenderMode` 类型定义（`'ndc-encode' | 'standard'`）
- `TriangleMesh` 类型定义
- 行为契约（调用时机、状态转换、错误处理）
- 返回值

### 2.4 处置声明

**不得仅添加注释而继续将其作为无约束的公开 API 暴露。**

本变更请求建议采用方案 A（@internal + API surface 测试），但最终处置需审查席裁定。

## 3. 变更项 3：NDC 容差规则

### 3.1 问题陈述

NDC 像素因果验证当前使用容差 2/255 ≈ 0.00784，但理论最坏情况线性上界为 0.00809，略超容差。审查席要求提供正式误差模型和容差选择依据。

### 3.2 误差模型正式定义

#### 3.2.1 编码量化误差 $E_{quant}$

**编码函数**：
$$e = \lfloor (n + 1) \times 127.5 + 0.5 \rfloor, \quad n \in [-1, 1]$$

**解码函数**：
$$n' = \frac{e}{255} \times 2 - 1 = \frac{e}{127.5} - 1$$

**误差推导**：
对于编码值 $e$，原始 NDC $n$ 的范围为：
$$n' - \frac{1}{255} \le n < n'$$

因此最坏情况量化误差：
$$E_{quant} = |n' - n| \le \frac{1}{255} \approx 0.00392$$

**为什么不是 0.5/255**：
常见的半量化步长 $0.5/255$ 适用于"编码值是桶中心"的情况。但本实现中，解码值 $n' = e/127.5 - 1$ 恰好是编码桶的**上界**（不是中心），因此最坏情况误差是完整的一个桶宽 $1/255$，而不是半桶宽 $0.5/255$。

验证：$n=0$ 时，$e=\lfloor 127.5+0.5 \rfloor = 128$，$n'=128/127.5-1=0.00392=1/255$。

#### 3.2.2 亚像素采样误差 $E_{sampling}$

**来源**：点图元（gl_PointSize=5.0）光栅化时，点中心与像素网格的亚像素对齐偏移。

**数学定义**：
NDC 坐标 $(x, y)$ 映射到屏幕坐标：
$$s_x = \frac{x+1}{2} \times W, \quad s_y = \frac{1-y}{2} \times H$$

如果 $s_x, s_y$ 不是整数，点中心位于亚像素位置。readPixels 读取点覆盖区域的中心像素，编码值可能受到点边缘的影响。

**最坏情况估算**：
$$E_{sampling,x} \le \frac{0.5}{W/2} = \frac{1}{W} = \frac{1}{320} \approx 0.003125$$
$$E_{sampling,y} \le \frac{0.5}{H/2} = \frac{1}{H} = \frac{1}{240} \approx 0.00417$$

**适用条件**：
- 仅适用于 POINTS 图元 + readPixels 测试路径
- 假设点大小足够大（gl_PointSize=5.0），中心像素被正确覆盖
- 实际值取决于点中心与像素网格的对齐，**不是固定常数**

**实测验证**：9 个顶点中，x 方向误差均为 0.0039（恰好为量化误差，亚像素误差≈0）；y 方向最大误差 0.0052（量化误差 0.0039 + 亚像素误差约 0.0013）。说明实际亚像素误差远小于最坏情况估算。

#### 3.2.3 浮点运算误差 $E_{float}$

GPU highp float（IEEE 754 单精度），矩阵乘法（4×4 × 4×1）约 16 次乘法 + 12 次加法：
$$E_{float} < 10^{-6}$$

与量化误差和亚像素误差相比，可忽略。

#### 3.2.4 误差合成模型

**采用最坏情况线性上界**（保守估计，适用于安全关键断言）：

$$E_{total} \le E_{quant} + E_{sampling} + E_{float}$$

**x 方向**：
$$E_{total,x} \le \frac{1}{255} + \frac{1}{320} + 10^{-6} \le 0.00392 + 0.003125 + 0.000001 \le 0.00705$$

**y 方向**：
$$E_{total,y} \le \frac{1}{255} + \frac{1}{240} + 10^{-6} \le 0.00392 + 0.00417 + 0.000001 \le 0.00809$$

**为什么用线性上界而非统计独立模型**：
- 各误差项可能相关（例如亚像素偏移可能同时影响编码和采样）
- 统计独立模型假设误差服从特定分布，但缺乏足够样本验证
- 安全关键断言应采用保守的最坏情况线性上界

### 3.3 容差选择

| 方案 | 容差 | y 方向理论上界 | 安全边际 | 实测最大误差 |
|---|---|---|---|---|
| 当前 | 2/255 ≈ 0.00784 | 0.00809 | -3.2% | 0.0052 |
| 建议 A | 3/255 ≈ 0.01176 | 0.00809 | 31% | 0.0052 |
| 建议 B | 维持 2/255 + 标注 | 0.00809 | -3.2% | 0.0052 |

**审查席裁定**：暂不批准从 2/255 放宽到 3/255。

**REV-08 proposed 规则**：
- 维持当前容差 **2/255**
- 在契约中明确标注："理论最坏情况线性上界（y 方向 0.00809）略超容差 2/255（0.00784），容差基于实测验证（9 顶点最大误差 0.0052），非理论最坏情况覆盖"
- 新增异常值检测策略：若任一顶点误差 > 1.5/255（0.00588），触发 WARNING 日志，记录该顶点的预期值、实测值和误差，供人工审查
- 若未来实测误差超过 2/255，必须重新审查误差模型，不得随意放宽容差

### 3.4 对异常值的检测策略

1. **硬断言**：误差 > 2/255 → 测试 FAIL
2. **软警告**：误差 > 1.5/255 → 测试 PASS 但输出 WARNING，记录顶点 ID、预期值、实测值、误差
3. **信息记录**：所有 9 个顶点的预期值、实测值、误差均记录到 E2E 证据 JSON
4. **趋势监控**：多次运行的误差趋势记录，检测漂移
